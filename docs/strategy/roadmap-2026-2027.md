# llm-governance-gateway: Strategic Roadmap 2026 to 2027

Nov 3, 2026 · @Michael Pointer

The gateway should become the governance runtime for agent loops, not a better proxy. Every competitor sits on the wire and sees requests. This library runs inside the process and can see the loop, the tool calls, the judge score and the human review decision as one governed run. That is the position no proxy can take, and the roadmap below is built around it.

**How this document was produced, and where the brief did not fit.** The brief you supplied is written for a user-facing application with a UI, user accounts, a retrieval stack and engagement loops. This repository is a TypeScript library that other applications embed. It has no frontend, no end users of its own, no vector store, no knowledge graph and no ontology. I did not invent any of those. Where a phase of the brief maps onto something real here, it is covered: Graph RAG becomes the provenance graph of a governed run, ontology becomes a typed policy schema keyed on autonomy and risk, decision intelligence becomes the counterfactual ledger and the TrustGate confidence model, and engagement becomes adopter retention and the compounding value of the ledger. Where a phase does not map, the section says so in one line and moves on. Every implementation claim below cites a file. Every market claim cites a URL and a date, and the sources are mostly vendor-written, which the competitive section flags.

## 1. Executive strategic assessment

**Recommended direction.** Reposition from "governance library for LLM calls" to "governance runtime for agent runs". Ship run-scoped budgets, governed tool calls and shadow calls in the next six months, freeze 1.0 behind them, and build the control plane as the sibling package already specced. Do not build a proxy, a hosted service, a Python port or a semantic cache.

**Where the product is strong today.** Three things no competitor combines, all verified in source: spend caps enforced in-process against the adopter's own database before every call (`src/gateway.ts` `checkSpendCap`), schema-validation-aware failover with a repair retry (`callWithChain`, `execLink`), and a fully deterministic mock mode so the whole pipeline runs in CI with no keys. Since last week, guardrail hooks run on every path and on cache hits through one shared front door, and the TrustGate confidence and human-review routing math has a TypeScript home (`src/trustgate.ts`). The ledger is correct under failure: aborted attempts write zero-token rows, stream failovers are ledgered per link, and batch spend is reserved then reconciled.

**Where the architecture is strong.** Every extension point is a small TypeScript interface the adopter implements (`UsageStore`, `PromptStore`, `ModelConfigStore`, `TaskOverrideStore`, `RateLimiter`, `CacheStore`, all in `src/types.ts`), and every provider integration is bring-your-own (`providers.factories`, BYO Anthropic client, `RedisLike`). Five runtime dependencies. The SPI has survived three adopters without a type-level break. The one structural weakness, duplicated front doors, was removed in PR #66.

**Competitive position.** Every named competitor is a proxy or a hosted control plane: LiteLLM, Portkey, Kong, Cloudflare, Vercel, Helicone, Bifrost, TrueFoundry. In the last six months the category has consolidated toward security platforms (Palo Alto Networks acquired Portkey in May 2026) and toward agent traffic (Kong Agent Gateway April 2026, LiteLLM MCP gateway, Cloudflare dollar spend limits June 2026). Gartner sizes the AI gateway segment at roughly $251M in 2026 and calls it embryonic. This library is not competing for that segment. It competes for the TypeScript teams who will never route production traffic through a sidecar, and for the governance questions a proxy structurally cannot answer: what did this agent run cost end to end, which tool calls did it make, was the cheaper model good enough, and what did the human reviewer decide.

**The three opportunities that matter.**

1. **Run-scoped governance.** A proxy sees HTTP requests. The library sees the agent loop. A budget, a step ceiling, a cost-velocity breaker and a ledger row per step, all keyed to one run id, is the capability Gartner's May 2026 guidance describes (governance scaled to the agent's autonomy level) and that every FinOps source in the research names as the control for runaway loops. Nobody in-process ships it in TypeScript.
2. **The counterfactual ledger.** The shadow-call design in `docs/design/hedging-and-shadow-calls.md` is the only route to answering "is Haiku good enough for this task" from the adopter's own traffic. The judge and the ledger already exist. Shadow mode is the missing primitive, and it turns the ledger into the dataset every routing decision should be made from.
3. **Closing the human loop.** TrustGate routes low-confidence outputs to review but nothing persists or resolves the review. A review queue in the control plane, with the decision written back to the ledger, gives the library labelled outcome data. That data is the one asset a competitor cannot copy.

**The biggest risks.**

- Scope drift toward a proxy. The HTTP layer in `src/http/app.ts` is a thin skeleton; growing it is the fastest way to become an undifferentiated LiteLLM.
- A 3,173-line `gateway.ts`. The front door is shared now; chain resolution is still three copies. The run-scoped work must not add a fourth.
- Single maintainer, three adopters, pre-1.0. Every month at 0.x with production adopters reads as hesitation. The SPI has earned the freeze.
- The in-process pitch is TypeScript-only by construction. That is the moat and the ceiling at once. Say so in the positioning rather than pretending otherwise.

### 2.2 Implemented, partial, dormant

**Fully implemented and tested**

- The governed pipeline per call: rate limit, per-user and per-org and global spend caps with observe mode, cache keyed to prompt fingerprint, chain failover with repair retry and ZDR filtering, usage ledger, sampled budget-aware judge with gate mode (`frontDoor`, `callWithChain`, `runJudge` in `src/gateway.ts`).
- Timeouts as ledger correctness: per-attempt and whole-operation deadlines, stream stall clocks, aborted attempts ledgered as zero-token rows (`src/deadline.ts`, `logAbortedAttempt`).
- Streaming with mid-stream failover and a documented degradation contract (`streamStructured`, `src/stream-guard.ts`).
- Native Anthropic path: thinking, cache\_control, server-side web search, cache-token pricing (`src/anthropic-native.ts`).
- Task routing with per-task chains, admin pin, tiers including a judge tier, store-backed overrides with TTL (`src/tasks.ts`, `ModelConfigStore`).
- Guardrail hooks pre and post on every path and on cache hits, verdicts ledgered, fail-closed by default (`src/guardrails.ts`, `frontDoor`, `applyPostGuardrail`).
- TrustGate: lexical grounding, business rules, weighted confidence blend, HITL routing with risk and stake adjustments, numerically pinned to the Python original (`src/trustgate.ts`, `src/trustgate.test.ts`).
- Multi-tenancy by optional `orgId` through every store and cache key.
- Live model discovery with static fallback; OpenRouter pricing auto-sync (`src/discovery.ts`).

**Partially implemented**

- Human-in-the-loop: `routeToHitl` decides, nothing persists the decision or resolves it. `onRoute: "allow"` is a calibration mode that only ledgers.
- Batch guardrails: the post hook at reconcile sees `prompt: ""` and `input: undefined` because the job store keeps no per-item prompt.
- Observability: OTel attribute mapping exists, no exporter, and the GenAI conventions it targets are still in Development status upstream.
- Pricing: 11 built-in rates, dated, with a monthly staleness check. No cached-input rates for OpenAI. Everything else is adopter-supplied.
- HTTP layer: constant-time token compare is absent; `/models` and `/tasks` are open to any app token.

**Designed, not built**

- Shadow and race calls (`docs/design/hedging-and-shadow-calls.md`, 492 lines of spec).
- The control plane sibling package, four layers (`docs/design/admin-control-plane-package.md`, 598 lines of spec, zero code).

**Dormant or deliberately held**

- The admin UI reference sketch (`docs/design/admin-ui-reference.md`), superseded.
- `requireExplicitDefault` strict mode, off by default.

### 2.3 Architectural leverage map

| Existing component | What it enables with little new code | What it cannot do without new infrastructure |
| --- | --- | --- |
| `frontDoor()` and `applyPostGuardrail()` | Any new per-call check lands on every path at once; a run-scoped budget is one more parameter through the same door | Cannot see across calls: there is no run id, no step index, no parent trace |
| `AttemptBudget` / `deadline.ts` | Already composes per-attempt and whole-call clocks; a run-level clock is the same shape one level up | Not persisted; a run that spans processes needs the budget in the store |
| `UsageEntry` with `traceId`, `metadata`, `guardrails` | The ledger is already the audit trail; a `runId` and `stepIndex` column turns it into a provenance graph queryable by SQL | No graph store, and none is needed: lineage is a tree over rows |
| Judge + `JudgeScore` table + `estimateForLink` | Shadow mode needs only a second link invocation and a `shadowOf` reference; scoring and pricing exist | Statistical comparison and a recommendation report are new |
| TrustGate `computeConfidence` with explicit `CONFIDENCE_WEIGHTS` | Weights are data, so calibration from labelled outcomes is a fit, not a rewrite | Labelled outcomes do not exist until HITL decisions persist |
| `ModelConfigStore` / `TaskOverrideStore` / `PromptStore` | The read side of a control plane is done; the write side is the sibling package's job | Write side, versioning, authorisation, UI |
| Mock mode + `inputText`/`outputText` snapshots | A ledger row is already a replayable fixture; a harness is a loader plus the mock responder registry | Snapshots may be encrypted; the harness must take the decrypt hook |
| AI SDK v7 `generateText` with `tools` and `maxSteps` | The agent loop primitive exists in the dependency; governing it is wrapping each step through the front door | Per-tool pricing and tool-call ledger rows are new concepts |

**Bottlenecks.** Chain resolution is still implemented three times (`runStructured`, `runText`, `streamStructured`); the run-scoped work should unify it rather than add a fourth. The job store has no per-item state. `gateway.ts` is large enough that reviewers will stop reading it; the run-scoped feature belongs in its own module.

### 3.3 Market trends that matter here

1. **Governance is moving to the agent run, not the request.** Gartner's 26 May 2026 press release says uniform governance across agents leads to failure and recommends governance scaled to each agent's autonomy level. Its 28 Apr 2026 release reports only 13% of organisations believe they have the right agent governance. Kong, LiteLLM and Portkey all shipped agent or MCP gateways in 2026. A proxy can govern the traffic; only something inside the process can govern the loop.
2. **Runaway agent cost is now a named FinOps problem.** The State of FinOps 2026 reports 98% of respondents manage AI spend, up from 63%. AWS launched a FinOps agent (Jun 2026) and Google Cloud announced spend caps that pause AI workloads (FinOps X 2026). The practitioner consensus across the sources: a per-run budget checked before each model call, a hard step ceiling, and a cost-velocity breaker. One January 2026 arXiv paper (Agent Contracts) reports budget-constrained agents cut token use by about 90% on its test set, a small study.
3. **Dollar-denominated, scoped budgets are becoming standard** (Cloudflare Jun 2026, Vercel per-user budgets 2026, LiteLLM per key/team/org/model). This library has had them since 0.1. The differentiation is enforcement location, not existence.
4. **Consolidation into security platforms.** Palo Alto Networks acquired Portkey (May 2026). Gartner published a Market Guide for Guardian Agents (Feb 2026). Governance is being bought as security. The library's natural buyer is the engineering team that owns the application, not the CISO, and the positioning should say so.
5. **Observability conventions are not settled.** As of Sep 2026 every OpenTelemetry GenAI attribute is still in Development status, and the conventions moved to a dedicated repository in Jun 2026. Building a heavy exporter now means rebuilding it. Keep the attribute mapping current and let adopters' collectors do the rest.
6. **LLM-as-judge in production is normal, and it costs money.** Braintrust, Langfuse and Arize all run judges on sampled production traces and bill for it. The library's budget-aware judge that refuses to breach the cap is a sharper version of the same idea.
7. **MCP tool-level budgets are a recognised gap.** An August 2026 feature request on a security-scanning MCP gateway asks for per-tool spend caps and circuit breakers because none existed there. Vendor pages describe deny-by-default tool lists and re-checking authorisation at execution time.

**What does not apply.** Graph RAG, knowledge graph construction and ontology-driven retrieval are real trends in the brief's domain. They have no bearing on a governance library's competitive position, and no competitor in this category ships them. The one honest mapping is in section 6.7: the ledger as a provenance graph of a run.

### 4.1 Reading the table

**Quick wins worth doing anyway, despite low scores:** 17 (1.0), 28 (#49) and 29 (#15) are small, unblock adopters, and the roadmap sequences them before the freeze. 10 (policy report) is the one quick win that is also differentiating: a compliance buyer can read it.

**High value, architectural investment required:** 1, 2, 8 together (the run ledger is the foundation; the budget and tool governance sit on it). 4 and 9 together (the review queue produces the labels; calibration consumes them). 7 and 11 together (the control plane).

## 6. Technical architecture proposals

Seven proposals. Each says what reuses existing code and what is new. File references are to `main` at 3e55779.

### 6.1 Run lineage and `GovernedRun`

**Problem.** The ledger has `traceId` per call and `metadata` for free-form attribution. It has no notion that calls belong together. An agent that makes nine model calls and four tool calls is nine unrelated rows.

**Data model.** Three nullable columns on `ai_usage_log` and `spend_cap_events`: `run_id` (text), `step_index` (integer), `parent_trace_id` (text). Rows written outside a run leave them NULL, so pre-1.0 rows and non-agent rows are indistinguishable, the same posture as `org_id` and `guardrails`. `ensureTables()` adds them; Drizzle schema exports gain the columns for `drizzle-kit`.

**Runtime.** A `GovernedRun` object created by `gw.startRun({ budgetCents, maxSteps, userId, orgId, route, metadata })`. It holds the run id, a running spend total, a step counter, a `AttemptBudget` for the whole run (reusing `src/deadline.ts`) and a cost-velocity window. Every existing entry point accepts an optional `run` in its options; `frontDoor()` reads it, stamps the lineage columns into `rowBase`, and adds a fourth cap check: `run.remainingCents()` against the estimate for this call. This is the one place the check lives, so every path gets it, which is the whole point of PR #66.

**Spend accounting.** The run total increments from the ledger row the call writes, never from an estimate, so the run's view of spend is the ledger's view. A `SpendCapError` with `scope: "run"` is the new breach kind; `spend_cap_events` records it like the others. Observe mode applies.

**Persistence.** In-process by default. `GovernedRun.snapshot()` and `gw.resumeRun(snapshot)` serialise the counters so a run that spans serverless invocations can continue; the store is the adopter's, as always.

**Reuse:** `frontDoor`, `checkSpendCap`, `AttemptBudget`, `SpendCapError`, `logUsage`. **New:** `src/run.ts` (about 250 lines), three columns, `explainRun()` later.

### 6.2 `runAgent()`: governed agent loop

**Problem.** AI SDK v7 `generateText` with `tools` and a stop condition runs a multi-step loop. Nothing governs the loop: no dollar budget across steps, no ledger per step, no guardrail on tool inputs.

**Design.** `gw.runAgent({ slug, input, variables, tools, maxSteps, run?, ...front-door options })`. Internally: `frontDoor()` once for the prompt and pre hook, then the AI SDK loop with `stopWhen` composed from `stepCountIs(maxSteps)` and a budget predicate, and an `onStepFinish` callback that writes one ledger row per step (`stepIndex` incrementing, `provider`/`model` from the step, tokens from the step's usage) and updates the run total. A step whose projected cost would breach the run budget stops the loop with `SpendCapError(scope: "run")` before the provider call; the partial result is returned on the error so the adopter can decide what to do with what was produced.

**Cost-velocity breaker.** A sliding window over the last N step costs; if the slope exceeds a configured cents-per-step growth factor (default off), the run stops with a `RunVelocityError`. This is the control the FinOps sources describe for slow runaways that a fixed cap misses.

**Guardrails.** The pre hook runs once on the rendered prompt as today. A new optional `guardrails.tool` hook runs before each tool execution (section 6.3). The post hook runs on the final text or object.

**Judge.** Sampled on the final output only. Judging intermediate steps is a frontier item.

**Verification before building.** Confirm the pinned `ai@^7` exposes per-step usage and a composable stop condition; if not, the loop is driven by hand with `generateText` per step, which is more code but gives the gateway full control. One spike day.

**Reuse:** everything in 6.1, `applyPostGuardrail`, `runJudge`. **New:** `src/agent.ts`, `RunVelocityError`, about 400 lines plus tests.

### 6.3 Governed tool calls

**Problem.** Proxies govern MCP traffic because that is what crosses the wire. In-process agents call AI SDK tools as functions; no gateway sees them. Tool calls are where the money and the risk are: a search API bills per call, a database write is irreversible.

**Design.** A `ToolPolicy` map in `GatewayConfig`: per tool name, `costCents` (fixed or a function of args), `maxCallsPerRun`, `maxCentsPerRun`, `requiresApproval`, `zdr`. `runAgent()` wraps each tool's `execute` so that before it runs: the per-tool and per-run caps are checked, the `guardrails.tool` hook runs with `{ tool, args, run, step }` and may allow, transform the args, or block, and if `requiresApproval` the run awaits `approvals.request()` (6.5). After it runs: a ledger row with `provider: "tool"`, `model: <tool name>`, `estimatedCostCents` from the policy, the args and result as `inputText`/`outputText` (encrypted if the hook is configured), and the guardrail record.

**Unknown tool pricing** warns once and ledgers zero, the same posture as local endpoints. A `preflightTools()` mirrors `preflightPricing()` so an adopter can fail startup on an unpriced tool.

**Why in-process beats a proxy here.** The gateway sees the typed arguments, the result, and which step of which run asked. A proxy sees a JSON-RPC body.

**Reuse:** `frontDoor`'s cap logic, `runGuardrail`, `logUsage`, the pricing warn-once pattern in `src/providers.ts`. **New:** `ToolPolicy` type, tool wrapping in `src/agent.ts`, `guardrails.tool` in `src/guardrails.ts`.

### 6.4 Shadow calls and the counterfactual ledger

The design is in `docs/design/hedging-and-shadow-calls.md` and this proposal follows it. Summary of what is built and how it uses 6.1.

**Design.** `shadow: { model: "openai:gpt-4.1", sampleRate: 0.1 }` per call or per task. The primary link runs and returns to the caller unchanged. Off the critical path, the shadow link runs to completion on the same prompt, is ledgered with `shadowOf: <primary traceId>` (one more nullable column) and `runId` shared with the primary, and both outputs are judged with the same criteria. The caller's latency does not change. The shadow's failure is a datum, not an error.

**Cap interaction.** Shadow spend counts against caps (it is real money). The budget-aware judge skip applies to both judgings. A `shadow.maxCentsPerDay` ceiling keeps the experiment bounded.

**What the data answers.** For each (task, primary model, shadow model) triple: paired judge scores, paired cost, paired latency, and the schema-failure rate of each. That is a paired comparison on identical inputs, which is what the ledger could never provide.

**Reuse:** `callWithChain` or `execLink` for the shadow invocation, `runJudge`, `estimateForLink`, `JudgeScore` table. **New:** `shadowOf` column, the off-path scheduler (fire-and-forget with the same failure isolation as observability hooks), about 300 lines.

### 6.5 Control plane L1 and L2 with the review queue

The sibling package specced in `docs/design/admin-control-plane-package.md`. This proposal adds the review queue to L1 and L2 and otherwise follows the spec, including its `system:seed` author exception for `seedPrompt`.

**L1 schema additions.** `review_queue` (id, usage\_log\_id, run\_id, document\_type, confidence, priority, routed\_at, decided\_at, decision, reviewer, notes) and `review_decisions` as the append-only history. The TrustGate `HitlDecision` already has the fields; the table is its persistence.

**L2 operations.** `reviews.enqueue(decision, usageLogId)` called from a shipped `post` hook wrapper around `trustGatePostGuardrail` (`onRoute: "enqueue"`), `reviews.list({ status, documentType })`, `reviews.decide(id, { decision: "approve" | "reject" | "edit", output?, reviewer })`. A decision writes a `review_decisions` row and, when the output was edited, a new ledger row with `provider: "human"` linked by `runId`, so the final answer and who gave it are in the same ledger as the model's.

**Approval gate.** `approvals.request({ run, step, tool, args })` returns a promise the run awaits; `approvals.grant(id)` resolves it. L2 ships a memory implementation and the SQL-backed one; the adopter wires the UI. A timeout default (configurable) denies.

**Boundary held.** No UI in the package. No auth. Takes the app's DB connection and a live `Gateway`, as the spec says.

### 6.6 Autonomy-tiered policy schema

**Problem.** Caps, judge sampling, HITL thresholds and ZDR are configured independently per task. Gartner's guidance, and common sense, is that they should derive from how autonomous and how risky the task is.

**Design.** `tasks.defaults` entries gain optional `autonomy: "assist" | "act-with-approval" | "act"` and `risk: "low" | "medium" | "high"`. A `policyTiers` table in config maps each (autonomy, risk) cell to defaults: `runBudgetCents`, `maxSteps`, `judge.sampleRate`, `hitlThreshold`, `requireZdr`, `toolsRequireApproval`. Explicit per-task or per-call settings override the tier. A task with neither field behaves exactly as today.

**Policy report.** `llm-gateway policy` renders the effective policy per task as markdown: which tier, which caps, which guardrails are configured, which models are ZDR-asserted, pricing as-of dates. This is the artefact a compliance reviewer or a customer's security questionnaire actually wants, and it is a pure read of config.

**On "ontology".** This is a typed policy schema, not an ontology. Calling it one would be marketing. It does give the library something no proxy has: policy that knows what the call is for.

### 6.7 The ledger as a provenance graph: `explainRun()`

**Problem.** "Why did this run cost $4.20 and produce that" is answered today by a human joining rows by `traceId` and `metadata`.

**Design.** `gw.explainRun(runId)` reads every row with that `run_id` from the `UsageStore` (one new SPI method, `listByRun(runId)`, optional with a fallback that scans by metadata), orders by `step_index`, and returns a tree: the run, each step, each tool call under its step, each guardrail verdict, each judge score, each shadow comparison, each review decision. A `toMarkdown()` renders it. This is the honest mapping of the brief's knowledge-graph phase: the graph exists, it is a tree over ledger rows, and it needs no graph database.

**What this is not.** Not Graph RAG, not entity extraction, not retrieval. The library does not read documents.

### 6.8 Ledger replay eval harness

`gw.replay({ rows, decrypt? })` loads ledger rows (from any `UsageStore` query the adopter runs) into mock-mode responders keyed by `promptSlug`, so a changed prompt or a changed guardrail can be run against last month's real inputs with zero provider spend, and the judge, in mock mode or against a cheap real model, scores the difference. Pairs with Braintrust-style CI gating without a new platform.

## 7. Agentic AI strategy

**The library is not an agent and should not become one.** The brief asks where autonomous agents, persistent memory and multi-agent orchestration fit. The honest answer for this product: it is the thing that governs them. Adopters already have agent frameworks (the AI SDK's own loop, LangGraph, the OpenAI Agents SDK). None of those enforce a dollar budget across a run against the adopter's database, ledger every step and tool call in one place, route low-confidence outputs to a human with a confidence model, or compare the chosen model against a counterfactual. That is the layer to own.

### 7.1 The architecture in one picture

```
  adopter's agent framework (AI SDK loop, LangGraph, custom)
            │  gw.runAgent() / gw.startRun()
            ▼
  ┌────────────────────────────────────────────────────────────┐
  │ GovernedRun: run budget, step ceiling, velocity breaker          │
  │   ├─ per step: frontDoor (rate limit, caps, cache, pre hook)     │
  │   ├─ per tool call: ToolPolicy caps, tool hook, approval gate    │
  │   ├─ chain failover, repair, ZDR filter (existing)              │
  │   ├─ post hook, TrustGate confidence → review queue              │
  │   ├─ judge (sampled), shadow call (sampled)                      │
  │   └─ one ledger row per step, tool call, verdict, review        │
  └────────────────────────────────────────────────────────────┘
            │ UsageStore (adopter's DB)        │ control plane (sibling pkg)
            ▼                                  ▼
  ledger as provenance tree          prompts, chains, caps, reviews, approvals
  (explainRun, replay, dry-run)      (headless ops, adopter's UI on top)
```

### 7.2 Autonomy levels and what each gets

Gartner's May 2026 guidance is that governance should scale with autonomy. The policy tiers in 6.6 encode that. The default mapping to propose, all overridable:

| Autonomy | Meaning | Default governance |
| --- | --- | --- |
| assist | Model produces, human acts | Caps and ledger. Judge sampled low. No approval gates |
| act-with-approval | Model proposes actions, human approves each irreversible one | Run budget and step ceiling required. Tools marked irreversible require approval. TrustGate routes below threshold |
| act | Model executes within bounds | Run budget, step ceiling and velocity breaker required. Per-tool caps required. Judge sampled high. Shadow sampling on. Any `high` risk task refuses `act` without an explicit override |

### 7.3 Where memory, planning and multi-agent fit

- **Persistent state.** The run is the unit of persistence (`snapshot`/`resumeRun`). The library does not store conversation memory; the adopter does. What the library persists is the governance state of the run: spend, steps, approvals pending.
- **Planning.** Out of scope. The adopter's framework plans; the gateway bounds the plan's cost and records what it did.
- **Multi-agent.** A sub-agent is a child run (`parentTraceId`, shared `runId` or a child `runId` with a parent link). Budgets nest: a child cannot spend what the parent has not got. This is the fan-out case the FinOps sources describe (four sub-agents each fanning out to four), and nesting the budget is the whole control.
- **Tool use and MCP.** In-process tools are governed by 6.3. MCP tools called through an MCP client in the adopter's process are the same shape once wrapped. Serving the gateway itself as an MCP server (backlog 21) is a frontier experiment, not a strategy.
- **Verification and recovery.** Schema repair and chain failover already exist per call. At the run level, a blown budget returns the partial result on the error; the adopter decides whether to resume with a top-up. The gateway does not retry a run on its own.

### 7.4 Where the judge, TrustGate and shadow calls fit together

Three instruments, three questions. The judge asks "was this output good" on a sample. TrustGate asks "should a human see this before it acts" on every call that configures it, deterministically and cheaply. Shadow asks "would another model have done better on this exact input" on a sample. The review queue turns TrustGate's routing into labelled outcomes; calibration (backlog 9) fits the confidence weights to those labels; the routing report (backlog 6) reads shadow plus judge. The loop closes inside the adopter's database. Nothing leaves.

### 7.5 Safety boundaries, stated

- The gateway never executes a tool the policy has not seen, never approves on a human's behalf, never auto-changes a chain. Recommendations are reports until a human changes config.
- Fail closed on guardrail error by default (`failOpen` is ledgered). Caps fail closed. Rate limiting fails open with an alert, as today, because a Redis blip should not take the application down.
- Every denial writes a row. An audit that cannot see blocked calls is not an audit, and that sentence is already in `src/guardrails.ts`.

## 8. Differentiation and defensibility

**The short version.** Features are copyable. Enforcement location and accumulated outcome data are not. The strategy is to make the ledger more valuable every month it runs and to make leaving mean giving that up.

### 8.1 What is defensible and why

| Source of advantage | Durability | Why |
| --- | --- | --- |
| In-process enforcement against the adopter's own database | High in the TypeScript niche | A proxy cannot move in-process without becoming a library, and the incumbents' business models are the proxy. Vercel is the only one that could, and its budgets are soft caps in a hosted plane |
| Deterministic offline CI for governance policy | High | Requires the mock-mode design from day one. Retrofitting it onto a proxy means a second product |
| The counterfactual ledger (shadow data) | Very high, compounding | Months of paired comparisons on the adopter's own traffic. No vendor can supply it, and switching libraries resets it |
| Labelled review outcomes and calibrated confidence | Very high, compounding | Same: the weights are fitted to this adopter's reviewers on this adopter's documents |
| Schema-aware failover and in-path gating judge | Medium | Copyable in principle; nobody in the gateway category has, because they are proxies that do not know the schema |
| Typed guardrail seam with ledgered verdicts | Medium | Copyable; the ledgering is the part competitors skip |
| Policy tiers keyed on autonomy and risk | Medium | Copyable, but it rides on the run ledger and the review queue, which are not |
| Seven providers plus BYO factories | Low | Deliberately not competing on breadth |

### 8.2 Switching costs, the honest kind

An adopter who leaves gives up: their ledger's lineage columns and what reads them, their shadow comparisons, their review history, their calibrated weights, their replay fixtures, and a test suite that runs their governance offline. None of that is lock-in by obscurity; the data is in their own tables in a documented schema. It is lock-in by accumulated value, which is the only kind worth having.

### 8.3 What competitors will do, and the response

- **Proxies add per-run budgets by agent id in headers.** Likely within a year; LiteLLM and Portkey already have per-key budgets and MCP gateways. Response: the in-process version sees tool arguments, typed outputs and the loop itself. Say so in the README comparison.
- **Eval platforms add gating.** Braintrust already blocks CI deployments. Response: the library gates in the request path with a budget-aware judge; position as complementary and ship an exporter to them.
- **Vercel AI Gateway hardens caps and adds a judge.** The real threat for TypeScript teams. Response: everything Vercel does is in its plane; everything this library does is in the adopter's database. Lead with that, and keep the AI SDK as the substrate so adopters never have to choose.

### 8.4 One to three years

Year one: the only in-process agent governance runtime in TypeScript, with 1.0 shipped and the counterfactual ledger live at three adopters. Year two: the ledger drives routing and review calibration at each adopter; the control plane is the standard write side. Year three: optional anonymised cross-adopter benchmarks, which no proxy vendor can produce because they do not hold judge scores against schema-validated outputs on identical inputs.

### 9.3 AI quality metrics the ledger already carries

Judge overall score by task and model; guardrail block and transform rates by hook; schema-repair rate and chain fall-through rate per link; cache hit rate; cost per successful call. These exist today in `ai_usage_log` and `ai_judge_scores` and need only a query. The control plane's L2 should expose them as functions so every adopter does not write the same SQL, which is the same argument the control-plane spec makes about stores.

### 9.4 Cost per successful task

The metric the agent features make possible for the first time: run spend divided by runs that completed without a cap breach, a guardrail block, or a reviewer rejection. Before 6.1 there is no run to divide by. Establish it per task in the first month after lineage ships and treat every later initiative as a change to this number.

## 11. Product vision, 12 to 24 months

A TypeScript team ships an agent the way they ship a database query today. They wrap it in a governed run, name the task, and declare how autonomous it is allowed to be. The gateway does the rest inside their process and inside their database: it caps what the run can spend, stops a loop that is accelerating, prices every tool call, blocks the prompt a policy says it should block, routes the output a confidence model says a human should see, and writes every one of those decisions to a ledger the team already owns. None of it crosses a wire they do not control. All of it runs in CI with no API keys.

After a quarter, the ledger starts paying for itself. The team asks whether the cheaper model is good enough for their highest-volume task and gets an answer with paired evidence from their own traffic. Their reviewers' decisions have calibrated the confidence model to their documents, so fewer outputs are routed and the ones that are deserve it. A prompt change is replayed against last month's real inputs before it ships. A security questionnaire is answered with a generated policy report rather than a week of writing.

After two years, this is the default answer to "how do we govern agents in TypeScript", in the same way the AI SDK became the default answer to "how do we call models". It sits under the AI SDK, not beside a proxy. Adopters who run it have a dataset no vendor can sell them: how every model they use behaves on their own inputs, scored, priced and reviewed. Some of them opt into comparing notes.

What it will not be: a hosted service, a proxy, a 100-provider adapter, a Python library, or a product with a dashboard of its own. Those exist. This is the thing that makes them unnecessary for the teams it serves.

## 12. Final recommendation: the seven questions

**1. The three most strategically valuable features to build first.** Run lineage with `GovernedRun` (backlog 8 and 1), governed tool calls (2), and shadow calls (3). The first two are one investment and give the library the position no proxy can take. The third turns the ledger into the dataset everything later is built on.

**2. The single feature that creates the greatest differentiation.** Shadow calls. Every competitor can add a per-run budget within a year. None of them hold schema-validated outputs, judge scores and prices for two models on identical inputs inside the adopter's database, and none can get there without becoming a library. It is also the feature whose value grows with every month of traffic.

**3. The feature that most increases retention.** The review queue with calibration (4 and 9). Once an adopter's reviewers have labelled a few hundred outputs and the confidence weights are fitted to them, leaving means starting over with defaults that are worse. That is retention through accumulated value, and it is the only honest kind for a library.

**4. The architectural investment that unlocks the most.** Run lineage: three nullable columns and a `GovernedRun` handle passed through `frontDoor()`. It is a one-week change that `runAgent`, tool governance, shadow attribution, `explainRun`, the policy dry-run and nested sub-agent budgets all depend on. It must land before the 1.0 freeze.

**5. The most ambitious agentic capability that is realistically achievable.** Nested, budget-bounded sub-agent runs with per-tool caps, approval gates on irreversible tools, and a cost-velocity breaker, all ledgered as one tree a human can read with `explainRun()`. It is ambitious because nobody ships it in-process; it is realistic because every component except the tree exists today and the tree is three columns.

**6. What the product should avoid building.** A semantic cache, a built-in prompt-injection classifier, a hosted control plane, a Python port, a hundred providers, an admin UI, a bandit router before a human has read a year of shadow reports, and any OpenTelemetry exporter heavier than attribute mapping while the conventions are still in Development. Each is either solved elsewhere, off-mission, or premature.

**7. If I were the product owner, the next 90 days.** Exactly section 10: close the three small SPI issues, land run lineage and the governed run, ship `runAgent` with tool governance behind observe mode at one adopter, generate the policy report, freeze 1.0. The reasoning is that the market has decided agent governance is the problem (Gartner, every gateway vendor's 2026 release, the FinOps surveys) and has decided to solve it at the proxy. That leaves the in-process position empty in TypeScript. Ninety days is enough to occupy it with a 1.0 behind it. Shadow calls and the review queue follow immediately as 1.1 and 1.2, because their designs are already written and their foundation will be live.

**One thing I would push back on in the brief itself.** The brief asks for engagement loops, Graph RAG, ontologies and digital twins. For this product those are the wrong instruments. The compounding loop that actually exists here is: adopter routes traffic, ledger grows, shadow and review data accumulate, routing and confidence improve, costs fall and quality holds, adopter routes more. That loop needs none of the brief's vocabulary and all of this roadmap.
